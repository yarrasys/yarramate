# A dragged position is presentation the repository keeps

Status: accepted

[ADR 0023](0023-state-comparison-visualization-is-adapter-presentation.md)
settled that visualization is adapter presentation: Core classifies, the
adapter colors, and derived styles are "presentation, not semantic claims."
Every case it covered was *derived* — computed fresh from the model on every
render, so nothing needed storing. Manual layout is the first presentation
state a user authors by hand, and a hand-authored position that vanishes on
reload is not layout, it is a gesture.

## Why an automatic layout is not enough

A projection document already stores its layout *algorithm*
(`presentation.layout`, `presentation.direction`), and `cytoscape-elk`
is deterministic: the same graph and the same options produce the same
coordinates. That covers the ordinary case and is genuinely reproducible,
which is why it belongs in the view.

It stops covering the case that motivated this: on a large graph — this
repository's own model is 289 subjects across 35 projections — a reviewer
declutters a corner by hand, because no algorithm knows that these four
components are the ones under discussion. Those coordinates are not
derivable from the model. Nothing in the graph implies them, and no
recomputation will reproduce them.

## Rejected: `.yarramate-out/`

[ADR 0027](0027-dogfooding-inputs-and-outputs-are-separated.md) splits
reviewable inputs under `.yarramate/` from reproducible, Git-ignored
artifacts under `.yarramate-out/`. A layout file looks like an output —
it is written by a tool, not typed into a document — so `.yarramate-out/`
was the first instinct.

It fails ADR 0027's own test. The directory is ignored by Git *because*
everything in it can be regenerated from the inputs; that is the property
that makes deletion safe. A dragged position cannot be regenerated by
anything. Putting it there means `git clean` silently discards work, a
clone starts from scratch, and a teammate never sees the arrangement the
reviewer built. The file is an input to rendering that happens to have been
authored through a canvas instead of an editor.

## Rejected: inside the projection document

The projection already carries `presentation`, and adding `positions`
there would need no new file. Two reasons against:

- Core validates projection documents. Coordinates would become something
  the semantic engine has an opinion about, and `check` would start
  adjudicating pixels — the exact confusion ADR 0023 exists to prevent.
- Positions churn on every drag while a projection's query is reviewed
  changes rarely. Sharing one file makes every arrangement a diff against
  a semantic input, and makes a semantic review noisy with coordinates.

## Rejected: coordinates on the concepts

Storing `x`/`y` beside a subject in an architecture document was rejected
outright: a position would become a claim, subject to `apply`, versioned in
the model's own history, and part of what an agent reads as declared
intent. ADR 0023's line — presentation is not a semantic claim — is
exactly this line.

## Decided

One adapter-owned sidecar per projection:
`.yarramate/visual-layout/<projectionId>.yaml`, a
`yarramate/visual-layout/v1` document carrying `format`, `projectionId`,
and `positions` (subject id → `{ x, y }`). Under `.yarramate/` because it
is a reviewable, committable input; a separate file per projection because
that is the unit a user arranges and the unit a diff should show.

Four properties keep it honest:

- **Never routed through `apply`.** It is not an operation, carries no
  claim, and lands with a direct `writeFileSync` on `layout.save` — the
  same precedent as `view.save` writing a projection file. Core never
  validates it; the adapter validates it against its own published schema.
- **Never `git commit`ed by the runtime.** Like a commit through
  [ADR 0084](0084-a-mechanical-edit-lands-through-apply-not-through-the-agent.md),
  a saved layout lands in the working tree and Git review decides whether
  it is kept. A reviewer who does not want to keep an arrangement discards
  the file.
- **Presentation must never fail a session.** An unreadable or invalid
  sidecar is skipped at session start, the same tolerance already applied
  to saved views. A malformed coordinate file must not stop a user from
  reading their architecture.
- **A sidecar for a projection that does not exist is rejected.** `layout.save`
  refuses an unknown `projectionId` rather than writing unreachable state.

## What this costs

- **Sidecars go stale.** Delete a subject and its position is an orphan
  entry the renderer ignores; nothing prunes it, and no diagnostic fires.
  Silence is the right failure for presentation, but it does mean the file
  accretes.
- **A layout is per-projection, not per-user.** Two people who disagree
  about an arrangement have a merge conflict in a coordinate file. That is
  the accepted consequence of making it reviewable, and it is the same
  tradeoff every checked-in editor config makes.
- **Positions are absolute.** They are interpreted against whatever the
  layout engine produced for the nodes that were not moved, so changing a
  projection's layout algorithm can leave pinned nodes sitting oddly until
  they are dragged again.
