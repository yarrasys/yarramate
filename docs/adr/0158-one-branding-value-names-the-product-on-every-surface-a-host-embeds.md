# One branding value names the product on every surface a host embeds

Status: accepted

A consumer that embeds yarramate presents it to people who have never heard
the name. ApertureX mounts the editor inside its own product; a consultancy
hosts workspaces under its own name; an agent connecting to a hosted
workspace reads whatever the tool list says. Before #546 the product name
reached those people in a handful of fixed places: the authority mark on the
editor's command strip ("Checked YarraMate model"), the workbook's cover
sheet ("YarraMate workbook", "Built by yarramate 1.31.0"), the LikeC4 model
banner ("Generated by YarraMate") and the generated project's name
(`yarramate-<project>`), and the tool list itself (`yarramate_design`,
`yarramate_apply`, the loop sentence that names them, the `initialize`
instructions that say "a YarraMate workspace"). Each was a literal in a
different module, so a host that wanted its own name had to fork the
sentence, and no host could reach the tool names at all.

## Decision

One `Branding` value, defined in `src/branding.ts` with no imports so it sits
under every published entry, and optional everywhere it is read:

```ts
interface Branding {
  productName: string          // "ApertureX"
  shortName?: string | null    // tight chrome; defaults to productName; null = logo alone
  logo?: { svg } | { url }     // the brand mark in the editor strip
  accent?: string              // one CSS colour for the chrome
  docsUrl?: string             // where the brand mark links
  vendorLine?: string | null   // "Powered by yarramate"; null removes it
  toolPrefix?: string          // "acme" publishes acme_design, acme_apply…
}
```

`resolveBranding(branding?)` applies the defaults once and is what every
surface reads. **Absent, every surface is byte for byte what it was**: the
gallery's committed LikeC4 export still reproduces, the workbook cover reads
as before, `TOOL_CATALOGUE` is unchanged, and the strip says "Checked
YarraMate model". That is the property the tests pin, and the reason the
unbranded product has no vendor line: "Powered by yarramate" under the name
yarramate is not a line anyone wrote.

**Where it is read.**

- `yarramate/tools`: `toolCatalogueFor(branding)` is `TOOL_CATALOGUE` with
  the prefix in every name, in the loop sentence and wherever a description
  names a sibling tool; `loopFor` and `instructionsFor` are the two
  sentences on their own. `runTool` takes any name: the verb after the last
  underscore dispatches, and a refusal names the tool by the name it was
  called by, so the agent that read `acme_export` in its list reads
  `acme_export` in the refusal. The stdio adapter publishes the unbranded
  rows and builds its instructions from `instructionsFor()`, so the two
  adapters still agree on the words.
- `ToolWorkspace.branding`: the host's context, beside `yarramateVersion`,
  from which the two exports that carry a name read it.
- The workbook's cover sheet (`00 Read Me`): the title, a vendor line under
  it, and "Built by ApertureX (yarramate 1.31.0)". With the vendor line
  removed the cover says nothing about the engine at all and the version
  lives in the hidden `~Meta` sheet alone. `~Meta` is machinery, keeps its
  keys, and is not branding.
- The LikeC4 export: "Generated by ApertureX." with the vendor line as the
  second comment, and `likec4.config.json`'s `name` becomes
  `<slug of shortName>-<project>`. The `yarramate.generated.json` marker,
  its digests and the ownership check keep their names: they are how the
  CLI recognises its own output, not what a person reads.
- `mountEditor` and `mountEditorWith` take `branding`. The command strip
  draws the brand mark (logo and short name, a link when `docsUrl` is set)
  before the title, says "Checked <short name> model", and ends with the
  vendor line. The strip is tight chrome: the authority line never wraps or
  shrinks (the title ellipsises instead), so it reads the short name, and a
  wordmark that already says the name passes `shortName: null` to draw the
  logo alone; the mark carries the product name as its accessible name. The accent is one CSS custom property, `--accent`, set on
  `.visual-shell`; the chrome that read `--eucalyptus` for emphasis (the
  authority mark, the notices, the changeset controls) reads `--accent` now,
  and the notation and the comparison marks read the named tokens as before,
  so a host's colour never reaches a node.

**Three decisions Nabeel took on 2026-09-16, as recommended.** Tool names may
be re-prefixed, default off: an instruction written for `yarramate_design`
will not find `acme_design`, so a host that re-prefixes owns its own agent
instructions, and the shipped skill file is not re-written for it. The
vendor line is removable, default on: a licensing call, held here as a
`null`. The CLI binaries and the `init` pointer are out of scope: white-
labelling is for the surfaces a consumer embeds or hosts, and a person
running `yarramate` at a terminal chose the name.

**What is refused.** A blank `productName`, or a `toolPrefix` an MCP client
could not publish (anything but letters, digits and hyphens; an underscore
would make the verb ambiguous), throws from `resolveBranding`: at mount or at
serve time, which is where a host's configuration error belongs, rather than
reaching a person as a blank name or an agent as a broken list.

## Consequences

Nothing on the wire and nothing in the record carries branding. A `closing`
frame's sentence is the host's already (ADR 0157); the rest of the shell's
copy stays the product's. The self-model gains `branding` served to the tools
entry, the browser, the LikeC4 adapter and the workbook function.

A hosted server that publishes `toolCatalogueFor(branding)` must dispatch
what it published: `runTool` accepts the names, but a list that says
`acme_design` and a dispatcher that checks for `yarramate_design` is the
server's bug, and `toolVerbOf` is there for the check.
